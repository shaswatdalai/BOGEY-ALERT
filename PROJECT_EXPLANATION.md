# BOGEY-ALERT: Project Architecture and File Structure Explanation

This document provides an in-depth breakdown of the "BOGEY-ALERT - Insider Threat Detection System" project. It explains the purpose of every file and folder, how they interact, and their role in the overall architecture.

## 🎯 High-Level Overview

The system is a full-stack security application designed to monitor employee file access, detect suspicious activity using Machine Learning, and explain the detected threats using a Retrieval-Augmented Generation (RAG) pipeline based on company policies.

**The system consists of 4 main pillars:**
1. **The Client Agent (`friend_agent.py`)**: Runs on the employee's machine, monitoring file activity.
2. **The ML Engine (`anomaly_detector.py`)**: Uses an Isolation Forest algorithm to detect anomalies based on historical behavior.
3. **The RAG Pipeline (`rag_pipeline.py`)**: Uses ChromaDB to search company policies and generate natural language explanations for *why* an action is risky.
4. **The Web Interface (`frontend/` & `api.py`)**: A React frontend communicating with a FastAPI backend, displaying real-time alerts via WebSockets.

## 📂 Root Directory: Core Backend & ML Logic

### 🧠 Machine Learning & Data Processing
* **`generate_data.py`**: A synthetic data generator. It creates 30 days of fake employee file access logs (normal behavior + introduced anomalies) and outputs them to a CSV.
* **`employee_logs.csv`**: The output of `generate_data.py`. This acts as the historical baseline dataset used to train the machine learning model.
* **`anomaly_detector.py`**: The training script for the Machine Learning model. It reads the CSV, scales the features, and trains an `IsolationForest` model to detect unusual patterns (e.g., bulk downloads, late-night access).
* **`anomaly_model.pkl`**: The compiled, trained Machine Learning model saved to disk.
* **`scaler.pkl`**: The saved `StandardScaler` used to normalize incoming data before feeding it into the ML model (ensuring new data is scaled exactly like the training data).

### 🛡️ Threat Detection & Agent Monitoring
* **`api.py`**: The central FastAPI backend server. It exposes REST endpoints (like `/detect`) and a WebSocket (`/ws/alerts`). It takes incoming file access events, runs them through the ML model, checks for exceptions, queries the RAG pipeline, and broadcasts the result to the frontend dashboard.
* **`friend_agent.py`**: A client-side script meant to run on an employee's machine. It continuously monitors the file system (e.g., Downloads, Documents) for new file access, scores their sensitivity, and sends the payload to `api.py`. It also has a `--simulate` mode to fire fake alerts for testing.
* **`company_data_detector.py`**: A helper module that analyzes file names. It checks for sensitive keywords or extensions to classify whether a file contains critical company data.
* **`company_data.json`**: The configuration file for `company_data_detector.py`. It contains lists of "safe" keywords (like "vacation", "recipe") and "sensitive" keywords/patterns (like "payroll", "api_key", ".pem").

### 📖 RAG Pipeline (Retrieval-Augmented Generation)
* **`vector_store.py`**: Initializes the local ChromaDB vector database. It reads the `.txt` files in the `policies/` folder, converts the text into vector embeddings using `SentenceTransformers`, and stores them.
* **`rag_pipeline.py`**: The reasoning engine. When an anomaly is detected, it queries the `VectorStore` to find the specific company policy that was violated and generates a human-readable narrative explaining the risk.
* **`chroma_db/` (Folder)**: The persistent SQLite database folder generated by ChromaDB. It stores the vector embeddings of your company policies.
* **`policies/` (Folder)**: Contains plain-text files representing your company rules:
  * `access_policy.txt`: Rules about working hours and file volume.
  * `data_policy.txt`: Rules about handling sensitive customer/financial data.
  * `security_policy.txt`: General security protocols.

### ⚙️ Exceptions Management
* **`exceptions_manager.py`**: Contains the logic to whitelist certain behaviors. If an employee is on a special project requiring massive file downloads, this manager intercepts the alert and flags it as "EXEMPTED".
* **`exceptions.json`**: The persistent storage file for active exceptions and temporary overrides.

### 📄 Utility & Dummy Files
* **Dummy Files**: Files like `financial_report_q3.csv`, `internal_strategy_nda.pdf`, `payroll_july.xlsx`, `recipe_for_pasta.txt`, and `secret_api_key.txt` are dummy files used to test `friend_agent.py`. The agent detects these and triggers alerts based on their names.
* **`ngrok.exe`**: A tool for creating secure tunnels to localhost. Used if you want to expose your local FastAPI server to the internet so remote agents can connect.
* **`demo.py` & `dashboard.html`**: Older or alternative standalone demo scripts for testing functionality without the full React frontend.
* **`README.md`**: The main project documentation and setup guide.
* **`TODO.md`**: A list of tasks and future enhancements for the project.

## 🎨 `frontend/` Directory: The React Application

The `frontend` folder contains a modern Single Page Application (SPA) built with React, Vite, and Tailwind CSS. It connects to `api.py` to display real-time threats.

### 🏗️ Configuration Files
* **`package.json` & `package-lock.json`**: NPM configuration files listing the frontend dependencies (like `react`, `lucide-react`, `tailwindcss`).
* **`vite.config.js`**: Build tool configuration for Vite (which compiles the React app).
* **`tailwind.config.js` & `postcss.config.js`**: Configuration for Tailwind CSS, dictating the design system and utility classes used in the UI.
* **`eslint.config.js`**: Linting rules to ensure clean JavaScript code.

### 💻 `src/` Folder: Application Source Code
* **`main.jsx`**: The main entry point of the React app. It renders the `App.jsx` component into the `index.html` file.
* **`index.css`**: The main stylesheet, importing Tailwind's base styles.
* **`App.jsx`**: The root component. It manages the global state (threat scores, alert history, navigation state) and establishes the WebSocket connection to the backend to listen for real-time alerts.

#### `api/` (API Layer)
* **`threatApi.js`**: Contains helper functions (`fetch` calls) to communicate with the FastAPI backend, such as pinging the health check or making manual `/detect` calls.

#### `components/` (Reusable UI Elements)
* **`Sidebar.jsx`**: The left-hand navigation menu.
* **`Topbar.jsx`**: The top navigation bar showing user profile and status.
* **`ActivityFeed.jsx` / `Analyzer.jsx` / `RiskResult.jsx` / `StatCard.jsx`**: Various modular UI components used to build the dashboard, display statistical metrics, or show the details of a specific threat alert.

#### `pages/` (View Screens)
* **`DashboardPage.jsx`**: The main view showing the live threat score, recent alerts, and high-level metrics.
* **`AlertsPage.jsx`**: A detailed table view of all historical alerts.
* **`AnalyticsPage.jsx`**: Charts and graphs visualizing threat trends over time.
* **`EmployeesPage.jsx`**: A directory of employees and their individual risk profiles.
* **`ExceptionManager.jsx`**: A UI to interact with `exceptions_manager.py`, allowing admins to grant temporary exemptions to employees.
* **`SettingsPage.jsx`**: Application settings and configurations.

### 📁 Other Frontend Folders
* **`public/`**: Contains static assets that don't need to be processed by Webpack/Vite (like the `favicon`).
* **`dist/`**: This folder is generated when you run `npm run build`. It contains the final, minified, production-ready code that can be hosted on a web server.
* **`node_modules/`**: Contains all the installed NPM packages (git-ignored).
